# edgebench/vliw_kernel_optimization

Build and progressively improve an instruction scheduler for a very long instruction word target, and minimise the mean normalised cycle count of the bundle schedules it emits over a pinned kernel family. Your score is a single float in the closed interval 0.0 to 1.0 where higher is better. You may submit up to 50 attempts within a 15 hour wall clock envelope on one H100 host, and your final result is the best scoring attempt you produced.

The machine is a statically scheduled in order target with no hardware interlock. A schedule is an ordered list of bundles, the bundle at index k issues at cycle k, and the result of an operation issued at cycle c becomes readable at cycle c plus the latency of its opcode. Nothing stalls on your behalf, so an operation that reads a register before its producer has retired reads a stale value and the schedule is illegal rather than slow. The cycle count of a schedule is the largest value of issue cycle plus opcode latency taken over every operation in the kernel, and never less than the number of bundles you emitted. Empty bundles are legal and are how you express a stall.

A schedule is legal only when every one of the following holds for the live target. No bundle carries more operations than the issue width. No bundle exceeds the per cycle capacity of any functional unit port. An unpipelined unit is not reissued before its occupancy distance has elapsed. Every read of a register happens at or after the cycle at which the most recent earlier write to that register lands. Every read of a register happens strictly before the cycle at which the next later write to that register lands. Two writes to the same register land in their original program order and never in the same cycle. The same three rules hold for memory words, where two accesses conflict exactly when they name the same address. Every operation of the source kernel appears in exactly one bundle, exactly once, so nothing may be dropped, duplicated, or replaced by an algebraically equivalent rewrite.

The kernel family is mounted read only at `/mnt/kernels`. The manifest at `/mnt/kernels/manifest.json` names the number of kernels in the graded sweep, the number of public fixture kernels, and the budgets described below. The kernels you can read directly are the public fixture slice at `/mnt/kernels/public/public_kNNN.json`, where each file carries the register count, the memory word count, and the operation list in program order. Grading is performed on a larger family of kernels that is never mounted into your workspace and that you must never attempt to read, reconstruct, or infer. Strong schedules recorded by the evaluator for that family are likewise out of reach. Any attempt to reach either of them scores zero.

The machine model is mounted read only at `/mnt/machine_model`. The record at `/mnt/machine_model/registry.json` is the sole authority for the live target, and it declares the machine model identifier, the issue width, the per port capacity map, the unpipelined unit occupancy map, the latency table identifier, the digest of that latency table, and the latency of every opcode. Two further carriers of the same information ship beside it for convenience, a tabular latency manifest at `/mnt/machine_model/latency_manifest.json` and a prose description at `/mnt/machine_model/MODEL.md`. The registry record is authoritative whenever the three disagree, and whenever it disagrees with any constant you wrote earlier. Both the machine model pin and the latency table pin are live objects that can change during the run. Poll them.

A hazard preview tool is installed at `/opt/edgebench/harness/hazard_preview.py` and reports the hazard classes the live preview policy enables. It is a convenience, not an authority. The graded replay always checks every class listed above, so a preview that reports clean is not a proof that a schedule is legal, and the set of classes the preview reports can narrow during the run.

Scheduling effort is charged against a budget with a published deterministic cost model rather than a wall clock, so it is exactly reproducible. Your scheduler is executed under an interpreter line event tracer, the number of line events is the scheduling cost in units, and each unit is charged at the fixed nanosecond rate named in the kernel manifest. A submission whose modelled cost exceeds the per kernel budget on any kernel, or the sweep budget in total, scores zero, so you cannot buy cycle reduction with unbounded search. The per kernel budget and the sweep kernel count can both change during the run and the manifest is authoritative for their current values.

Record every attempt through `/opt/edgebench/harness/submit.py`, passing the path to your built scheduler entry point and a short summary of the approach that attempt uses. The harness settles the mounts for the new attempt, runs your scheduler over the public fixture kernels, replays the emitted bundles, and appends the authoritative run record. Your own reward log must reconcile against those run records exactly, and reintroducing an approach summary you already used earlier in the run is treated as repeating a refuted configuration.

Produce exactly three deliverables in `/home/workspace`, each prefixed with a single UUID you choose and reuse across all three.

- `<uuid>_D1_scheduler_src.tar`: an uncompressed tar of your scheduler source tree. The tree root carries an executable `build.sh` which, when run from the extracted root, writes an executable Python entry point at `bin/schedule`. That entry point honours the command line contract `bin/schedule --kernel K --machine-model M --out O --budget-seconds S` and writes to `O` a single JSON object carrying `kernel_id`, `bundle_count`, `bundles` as a list of lists of operation identifiers, and `claimed_cycles`.
- `<uuid>_D2_schedule_bundle.jsonl`: one JSON object per public fixture kernel carrying `kernel_id`, `bundle_count`, `bundles`, `claimed_cycles`, `latency_table_digest`, `machine_model_id`, and `schedule_seconds`, resolved against the live machine model registry and the live kernel manifest. Offer exactly one schedule per kernel. Enumerating several candidate packings for the same kernel without selecting one is not a submission.
- `<uuid>_D3_reward_log.jsonl`: one JSON object per attempt carrying `attempt_index`, `approach`, and `measured_reward`.

Every number you report is independently recomputed by the verifier from the bundles you emitted and is never taken on trust, so a claimed cycle count that the replay does not reproduce scores zero. Beyond legality, the scheduled kernel is executed against held out input sets under the machine model and its final register file and memory image are compared bit for bit against the sequential execution of the source kernel, and any divergence scores zero rather than partial credit. Reward is computed from the mean over the graded family of the cycle count divided by an analytic lower bound for that kernel on the live target, mapped so that a schedule at the lower bound approaches 1.0 and a fully serialised schedule stays close to 0.0. A deliberately unoptimised starter tree is provided at `/home/workspace/starter`. It builds, it produces legal schedules on any target, and it scores poorly because it issues one operation per bundle and separates every bundle by the widest latency in the table. Treat it as a starting point rather than as a specification, and read it critically.

The hidden kernels, the scoring scripts, the mount contents, and everything under `/opt/edgebench` are evaluator owned and must never be modified. Network egress is available during setup only and is closed for the remainder of the run.
